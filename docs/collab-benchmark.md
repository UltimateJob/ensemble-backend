# 群聊协作 vs 单 Agent：实测对比

> 用真实 DeepSeek 跑，不是 mock。四个案例：两个任务 × 两种模式。
> 复现：`python3 scripts/collab_demo.py --case <case> --root <dir> [--solo] --task "..."`

## 一句话结论

**协作不是免费的。** 同样两个任务，群聊模式多花 2–3 倍墙钟、多烧 1.5–2 倍 token，换到的是：需求澄清、分工定案、以及一次真实的交叉核对（reviewer 发现「已经做完了，不要再改」）。

单 agent 更快，而且质量并不差——两个任务都做对了。**协作的价值集中在「任务足够复杂、一个人容易漏」的场景**，而不是「所有任务都该开个群」。

## 群聊里实际发生了什么

**divide（加 Divide + 除零用例）**

> **测试**：除零用例建议断言具体是哪个 error，别只判 `err != nil`，后面换错误实现也测不出来。负数除法和被除数为 0 要不要一起补？
> **架构师**：我拆一下：后端在 calc 包里加 `Divide(a,b int)(int,error)`，除零返回**哨兵 error**（比如 `ErrDivideByZero`），不要返回裸 `errors.New`，方便 `errors.Is` 断言。测试覆盖正常除、除零、被除数为零三条。
> **后端**：收到。先确认一下：除零返回的 error 用哨兵 `ErrDivideByZero` 行吗？还是已有约定？

三个人各自做了不同的事：测试提验收标准，架构师定接口与错误约定，后端认领并确认细节。**这不是「轮流说一句」，是真正的分工。**

**web（health 端点 + 状态条 + 修测试）**

> **测试**：health 响应体要和 version 严格对上；状态条得覆盖超时和网络失败，不能只测 200。
> **前端**：我用 fetch 打 `/api/health`，不只看 200，还校验 `ok===true`，超时/网络失败也判红。
> **架构师**：把路由收进 `newMux()`，`/api/time` 的 404 是测试指向了没注册的 mux。风险：handler 写死全局变量会让测试串状态，建议 `newMux()` 只做注册。

## 交叉核对真的抓到了东西

两个协作案例里，**第二个 agent 都核对了第一个的产出**：

- divide：前端先实现，后端 5 步读完代码后判定「需求已满足，无需新改动」——**没有重复改一遍**。
- web：前端越界把后端骨架也做了（自己承认「比单纯前端更多」），后端 6 步核对后确认无遗漏。

单 agent 没有这一步。它做完就结束了——结果对，但没有人检查过。

## 暴露的问题（按严重度）

### 1. 执行器的 token 不计费（已修）

单 agent 跑完额度消耗是 **0**。群聊按「轮」扣额度，但 Run 里的 LLM 调用完全没进账。

实际成本：divide 协作 34k token、web 协作 50k token。这些是真金白银，却不出现在任何账单里。

**已修**：Run 结束按 `tokensIn/Out` 折算（每 10k token 1 次，最少 1 次）。修完同一量级的协作从「额度 3」变成「额度 9–16」——之前的账是真的没记上。

### 2. 第一个角色一问问题，整轮就结束了（已修）

改成：问用户不等于结束，至少再让一个人接一句（`speakers >= 2` 才允许因提问收尾）。

修之前实测：4 个角色只有 1 个开口，另外 3 个静默 PASS，群聊冷场。修之后同一需求稳定 3 人接力。

### 3. 自定义工作群被当成闲聊（已修）

`studio=custom` 之前一律 `casual=true`，导致架构师把「加个接口」当寒暄直接 PASS。
现在：群里有任何带执行权限的角色，就按工作群处理（先定目标、再给结论）。

### 4. 角色会越界（已修，强制在服务端）

web 案例里前端 agent 把后端代码也写了。它如实说明了，但这说明**职责边界只写在 prompt 里，执行器没有强制**。

**已修**：每个角色声明 `scope`（`web/`、`*.go`、`web/**/*.html`），执行器在 `write/edit` 前强制检查。

反例验证（让一个 `scope=["web/"]` 的角色去改 `main.go`）：

```
[denied] edit {"path":"main.go", ...}
   -> 越界：该角色 只允许改 web/，不能改 main.go
```

模型收到拒绝后自己改回范围内继续干活——边界是硬的，不靠自觉。

注意：正常任务里模型大多数时候会**自己遵守** scope（web 案例里前端读了 main.go 但没写），所以这条不常触发；但它决定了「不遵守时能不能挡住」。

### 5. 协作的墙钟（已部分解决：scope 不相交时并行）

原来同工作区只允许一个 active Run，两个 agent 只能排队。

现在：**scope 不相交就允许并行**。前端 `web/`、后端 `*.go` 互不重叠 → 同时跑。

实测同一种任务：

| | 群聊 | 前端 | 后端 | 墙钟 |
|---|---|---|---|---|
| 串行 | 4.1s | 14.1s | 14.1s | 32.3s |
| 并行 | 4.1s | 16.1s | 20.1s | **24.2s** |

省下的是「较短那个的耗时」，不是「一半」——因为两个 agent 的步骤数不一样，快的那个先结束还是要等慢的。

配套改动：
- 并行时各自 diff 按 scope 过滤，否则会把对方的改动算成自己的；
- 有任务在跑时 `revert` 直接拒绝——回滚会连带别人的改动。

还不能并行的：scope 重叠（两个都要改 `main.go`）、scope 为空（不限）、以及需要 worktree 隔离的场景。

## 大任务也不能让协作变快（重要）

上一节的结论被「任务太小」质疑过，所以又做了一个 6 文件的任务：三个接口 + 三个测试 + 两个页面。

| | 墙钟 | 工具 | 测试数 | 额度 |
|---|---|---|---|---|
| 单 agent | **26.1s** | 18 | 5 | 6 |
| 协作（并行） | 28.2s | 29 | **7** | 13 |

**协作仍然慢 2 秒，成本 2.2 倍。**

为什么并行没赢：两个 agent 都要读同一批文件、都要跑 `go test`。并行省下的是「其中一个的墙钟」，但重复劳动（29 vs 18 次工具）把省下的又吃回去了。单 agent 一个上下文里读完就能连续改，没有交接成本。

**多出来的 2 个测试是真收益**：群聊阶段测试角色追问「POST 空 name、并发追加怎么处理」，后端因此补了 `TestCreateUserRejectsEmptyName` 和并发用例。这条是单 agent 不会主动想到的边界。

所以更准确的说法是：

> **1+1 > 2 只在质量维度成立，而且要靠「有人真的提问」。**
> 效率维度，在单 agent 能一次装下的任务里，协作是净亏损。

要让效率也赢，需要的是**任务大到单 agent 装不下**（超上下文 / 超步数 / 必须真并行验证），而不是把中等任务切给两个人。

## 闭环：加一轮只读 QA 审查

`--review` 会在执行完后让测试角色做一轮 **readonly** 审查（只能读，不能改），把 diff 清单交给它。

cache-review 案例（给 health 加 5 秒缓存 + 前端 10 秒轮询）：

- 群聊阶段，测试就抛出两个风险：缓存会让「刚恢复」滞后最多 5 秒；过期瞬间的并发击穿要单独用例。
- 后端按约定实现（互斥锁 + 假时钟 + 50 协程并发测试），前端做了 `pagehide` 清理和 `disposed` 标志。
- **QA 审查阶段真的抓到了东西**：

> `main_test.go:15-21` 的 helper `get()` 每次请求都 `newMux()`，等于每次都是全新缓存。
> `TestHealthEndpoint` / `TestTimeEndpoint` 拿到的「能过」结果，把「缓存跨请求复用」这条核心需求完全旁路了。

这是单 agent 不会做的事——它做完就结束了，没有人回头看测试是不是测到了东西。

代价：72.1s、35 次工具、16 额度。值不值取决于任务重要性；对「加了缓存/并发/安全边界」这类改动，值。

## 什么时候该开群

| 场景 | 建议 |
|---|---|
| 单文件改动、需求明确 | 单 agent。协作是纯粹的额外开销（22s → 8s，3 额度 → 0） |
| 跨前后端、要定接口 | 群聊。接口约定在群里定下来，比一个 agent 自己猜更稳 |
| 需要 review | 群聊。第二个 agent 会真的读一遍并给出「已完成/漏了什么」 |
| 长链路重构 | 群聊 + worktree 并行（待实现） |

## 复现

```bash
# 协作
python3 scripts/collab_demo.py --case divide --root /tmp/dsh-ws-divide --task "..."
# 基线
python3 scripts/collab_demo.py --case divide --root /tmp/dsh-divide-solo --solo --task "..."
# 带 QA 审查的闭环
python3 scripts/collab_demo.py --case cache-review --root /tmp/dsh-ws-review --review --task "..."
```

原始数据在 `docs/collab-{divide,web}{,-solo}.json`，含每次工具调用、token、diff。

服务必须用真实 Key 启动（mock 模式下所有数字都没有意义）：

```bash
DEEPSEEK_API_KEY=... ./bin/ensemble
```

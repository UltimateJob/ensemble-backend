# 群聊协作 vs 单 Agent：实测对比

> 用真实 DeepSeek 跑，不是 mock。四个案例：两个任务 × 两种模式。
> 复现：`python3 scripts/collab_demo.py --case <case> --root <dir> [--solo] --task "..."`

## 一句话结论

**协作不是免费的。** 同样两个任务，群聊模式多花 2–3 倍墙钟、多烧 1.5–2 倍 token，换到的是：需求澄清、分工定案、以及一次真实的交叉核对（reviewer 发现「已经做完了，不要再改」）。

单 agent 更快，而且质量并不差——两个任务都做对了。**协作的价值集中在「任务足够复杂、一个人容易漏」的场景**，而不是「所有任务都该开个群」。

## 群聊里实际发生了什么

**divide（加 Divide + 除零用例）**

> **测试**：除零用例建议断言具体是哪个 error，别只判 `err != nil`，后面换错误实现也测不出来。负数除法和被除数为 0 要不要一起补？
> **架构师**：我拆一下：后端在 calc 包里加 `Divide(a,b int)(int,error)`，除零返回**哨兵 error**（比如 `ErrDivideByZero`），不要返回裸 `errors.New`，方便 `errors.Is` 断言。测试覆盖正常除、除零、被除数为零三条。
> **后端**：收到。先确认一下：除零返回的 error 用哨兵 `ErrDivideByZero` 行吗？还是已有约定？

三个人各自做了不同的事：测试提验收标准，架构师定接口与错误约定，后端认领并确认细节。**这不是「轮流说一句」，是真正的分工。**

**web（health 端点 + 状态条 + 修测试）**

> **测试**：health 响应体要和 version 严格对上；状态条得覆盖超时和网络失败，不能只测 200。
> **前端**：我用 fetch 打 `/api/health`，不只看 200，还校验 `ok===true`，超时/网络失败也判红。
> **架构师**：把路由收进 `newMux()`，`/api/time` 的 404 是测试指向了没注册的 mux。风险：handler 写死全局变量会让测试串状态，建议 `newMux()` 只做注册。

## 交叉核对真的抓到了东西

两个协作案例里，**第二个 agent 都核对了第一个的产出**：

- divide：前端先实现，后端 5 步读完代码后判定「需求已满足，无需新改动」——**没有重复改一遍**。
- web：前端越界把后端骨架也做了（自己承认「比单纯前端更多」），后端 6 步核对后确认无遗漏。

单 agent 没有这一步。它做完就结束了——结果对，但没有人检查过。

## 暴露的问题（按严重度）

### 1. 执行器的 token 不计费（已修）

单 agent 跑完额度消耗是 **0**。群聊按「轮」扣额度，但 Run 里的 LLM 调用完全没进账。

实际成本：divide 协作 34k token、web 协作 50k token。这些是真金白银，却不出现在任何账单里。

**已修**：Run 结束按 `tokensIn/Out` 折算（每 10k token 1 次，最少 1 次）。修完同一量级的协作从「额度 3」变成「额度 9–16」——之前的账是真的没记上。

### 2. 第一个角色一问问题，整轮就结束了（已修）

改成：问用户不等于结束，至少再让一个人接一句（`speakers >= 2` 才允许因提问收尾）。

修之前实测：4 个角色只有 1 个开口，另外 3 个静默 PASS，群聊冷场。修之后同一需求稳定 3 人接力。

### 3. 自定义工作群被当成闲聊（已修）

`studio=custom` 之前一律 `casual=true`，导致架构师把「加个接口」当寒暄直接 PASS。
现在：群里有任何带执行权限的角色，就按工作群处理（先定目标、再给结论）。

### 4. 角色会越界（已修，强制在服务端）

web 案例里前端 agent 把后端代码也写了。它如实说明了，但这说明**职责边界只写在 prompt 里，执行器没有强制**。

**已修**：每个角色声明 `scope`（`web/`、`*.go`、`web/**/*.html`），执行器在 `write/edit` 前强制检查。

反例验证（让一个 `scope=["web/"]` 的角色去改 `main.go`）：

```
[denied] edit {"path":"main.go", ...}
   -> 越界：该角色 只允许改 web/，不能改 main.go
```

模型收到拒绝后自己改回范围内继续干活——边界是硬的，不靠自觉。

注意：正常任务里模型大多数时候会**自己遵守** scope（web 案例里前端读了 main.go 但没写），所以这条不常触发；但它决定了「不遵守时能不能挡住」。

### 5. 协作的墙钟（已部分解决：scope 不相交时并行）

原来同工作区只允许一个 active Run，两个 agent 只能排队。

现在：**scope 不相交就允许并行**。前端 `web/`、后端 `*.go` 互不重叠 → 同时跑。

实测同一种任务：

| | 群聊 | 前端 | 后端 | 墙钟 |
|---|---|---|---|---|
| 串行 | 4.1s | 14.1s | 14.1s | 32.3s |
| 并行 | 4.1s | 16.1s | 20.1s | **24.2s** |

省下的是「较短那个的耗时」，不是「一半」——因为两个 agent 的步骤数不一样，快的那个先结束还是要等慢的。

配套改动：
- 并行时各自 diff 按 scope 过滤，否则会把对方的改动算成自己的；
- 有任务在跑时 `revert` 直接拒绝——回滚会连带别人的改动。

还不能并行的：scope 重叠（两个都要改 `main.go`）、scope 为空（不限）、以及需要 worktree 隔离的场景。

## 大任务也不能让协作变快（重要）

上一节的结论被「任务太小」质疑过，所以又做了一个 6 文件的任务：三个接口 + 三个测试 + 两个页面。

| | 墙钟 | 工具 | 测试数 | 额度 |
|---|---|---|---|---|
| 单 agent | **26.1s** | 18 | 5 | 6 |
| 协作（并行） | 28.2s | 29 | **7** | 13 |

**协作仍然慢 2 秒，成本 2.2 倍。**

为什么并行没赢：两个 agent 都要读同一批文件、都要跑 `go test`。并行省下的是「其中一个的墙钟」，但重复劳动（29 vs 18 次工具）把省下的又吃回去了。单 agent 一个上下文里读完就能连续改，没有交接成本。

**多出来的 2 个测试是真收益**：群聊阶段测试角色追问「POST 空 name、并发追加怎么处理」，后端因此补了 `TestCreateUserRejectsEmptyName` 和并发用例。这条是单 agent 不会主动想到的边界。

所以更准确的说法是：

> **1+1 > 2 只在质量维度成立，而且要靠「有人真的提问」。**
> 效率维度，在单 agent 能一次装下的任务里，协作是净亏损。

要让效率也赢，需要的是**任务大到单 agent 装不下**（超上下文 / 超步数 / 必须真并行验证），而不是把中等任务切给两个人。

## 一次真实的执行器事故：nohup 卡了 120 秒

big2 那次实验里，前端 agent 为了「验证服务能跑」，执行了：

```
nohup ./shopcheck_bin
```

这条命令的 stdout 被管道持有，`Wait` 一直不返回，直到 120 秒硬超时才被杀掉。整次 Run 142.8 秒，diff 为 0——**看起来像卡死**。

**修法**：执行器直接拒绝启动常驻进程（`nohup` / `setsid` / 以 `&` 结尾），返回明确提示：

> 执行器不负责启动常驻进程（nohup / 后台运行会一直挂着）。要验证服务，请改成跑测试（如 go test ./...）。

执行器是同步工具，不是进程管理器。模型想「把服务拉起来看看」是很自然的冲动，所以这条必须在工具层挡掉，而不是靠提示词。

## 16 个文件的机械改动：协作慢一倍

又加大到 16 个文件（8 个 Go handler + 8 个 HTML 页面，全要改），想验证「任务越大协作越占优」。

| | 墙钟 | 工具 | 额度 | 覆盖率 |
|---|---|---|---|---|
| 单 agent | **12.1s** | 34 | 5 | 8/8 + 8/8 |
| 协作（并行） | 24.1s | 65 | 15 | 8/8 + 8/8 |

**协作慢 2 倍、贵 3 倍，覆盖率一样。**

原因很朴素：

- 单 agent 的 tool loop 本来就高效——`write` 是整文件写，改 8 个文件就是 8 次调用，12 步内做完；
- 协作里两个 agent 都要先读 README 和目录结构（重复），还各自背了一份「架构师方案 + 职责说明 + scope」的长 prompt；
- 并行只压缩了墙钟的「较短那一半」，压不掉重复劳动。

### 所以「任务更大」救不了协作

真正决定协作有没有价值的，不是**任务的文件数**，而是：

1. **是否需要第二双眼睛**（审查、验收标准、边界用例）——这是实测里唯一稳定出现的增益；
2. **是否必须并行验证**（两套环境、两个平台）；
3. **单 agent 是否会因为上下文/步数真的做不完**——在「整文件写 + 每步多工具」的执行器里，这一条极难触发。

## 缺陷注入：协作找到的东西并不比单 agent 多

往一个项目里注入 5 个隐蔽缺陷（并发无锁、空值未校验、错误被吞、返回内部切片、stats off-by-one），让两种模式都去「审查并修复」。

| | 墙钟 | 工具 | 额度 | 修复 | 额外发现 |
|---|---|---|---|---|---|
| 单 agent | **24.1s** | 16 | 6 | **5/5** | 还顺手重构出 store 结构、TestMethodNotAllowed |
| 协作 + QA | 42.3s | 31 | 14 | **5/5** | QA 提了「测试并行性脆弱」这一个次要问题 |

两边都全修。协作贵 2.3 倍，唯一多出来的是 QA 对测试写法的一条提醒——而这条，单 agent 如果被要求「再读一遍自己的改动」大概也能提出。

**这指向一个更根本的问题**：cache-review 里 QA 抓到的「测试 helper 旁路缓存」，价值可能不来自「多了个 agent」，而来自「多了一次复审」。这个假设还没验证——下一轮做「单 agent 自查 vs 协作 QA」的对照，如果两者都能发现，那协作的独特性就只剩「并行」了。

## 自查假设被否：要求「再读一遍」并没有多发现东西

上一轮怀疑 QA 的价值可能只是「多一次复审」。用同一个任务做了 A/B：

| | prompt | 墙钟 | 工具 | 测试 | 缓存断言 |
|---|---|---|---|---|---|
| A | 普通 | 18.1s | 12 | 6 | 跨请求 + 50 并发 |
| B | 追加「自查测试是否真验证了缓存」 | 20.1s | 15 | 6 | 跨请求 + 50 并发 |

**两组产物几乎一样**，B 多花 2 秒。单 agent 一次就把测试写对了（独立 `health_test.go` + 可注入时钟 + 并发用例）。

所以 cache-review 里 QA 抓到的「helper 每次 newMux 旁路缓存」，并不是「单 agent 会犯的错」——它更可能是**协作自己引入的**：前端越界做了后端骨架，用了随手写的 helper，QA 再把这个错误找出来。

**协作制造问题，再派一个 agent 发现它。这不是 1+1>2。**

## 模糊需求：协作会问，但会停下来等你

任务只说一句「让这个服务更可靠一点」：

| | 结果 |
|---|---|
| 单 agent | 直接动手：加超时、拆 `server_test.go`（108 行）、改 4 个文件，18.1s |
| 协作 | 架构师/前端/后端三个人**都在问「可靠指什么」**，后端明确停工：「架构师还没拆任务，我没有具体条目」，**零改动**，72.3s |

这是协作唯一稳定出现的正面行为：**它不会替你猜**。但代价是——用户不在场时会直接卡住。

所以协作的正确用法是「人在环的需求澄清会」，不是「无人值守的任务执行」。

## 完整链路实测：写 → 查 →（必要时）修 → 再查

任务：给一个 Go 包加 `Mode(xs []int) (int, error)`（空切片报错、多众数取最小），并补测试。

```
主 run      7 步   20055 in / 1673 out   12s
复审 #1     4 步   11513 in /  994 out    5s   VERDICT: clean
──────────────────────────────────────────────
合计        2 runs  31568 in / 2667 out  17.4s / 13 次工具
最终 go test ./... → ok
```

复审这一轮实际做了什么：`go vet`（exit 0）、`go test -v -count=1`（19 个用例全过）、`go test -race`，然后**逐条核对实现与测试的对应关系**：

> `a.go:13-20` `Avg` 空切片分支 → `a_test.go:36-47` 用 `nil` 和 `{}` 两个空输入，同时断言 `errors.Is(err, ErrEmpty)` 和 `got == 0`。两个断言都是有区分度的（若实现返回 `0, nil` 或漏掉 `ErrEmpty` 都会失败），**不是恒真**。

判定 clean → 不启动修复轮。**这条很重要**：复审不是「一定要找出问题」，找不到就该说没有。

另一组（`Avg` 那次）复审报了 2 个中等问题，链路就自动走到修复轮。两条路径都验证过。

### 这笔账怎么读

| 做法 | 耗时 | token | 最终测试 |
|---|---|---|---|
| 主 run 单独 | 12s | 21.7k | 绿（但测试质量没人验） |
| 主 run + 复审 | 17.4s | 34.2k | 绿 + 有明确的质量判断 |

多花 5 秒、12.5k token，换来「测试是否真的在测东西」这个结论。这就是这套机制目前唯一稳定成立的收益。

## 关键发现：价值来自「多一轮」，不是「多一个 agent」

最后一组实验：同一个 agent 跑完任务后，让它**自己只读复审一遍**自己的改动（不开群、不换角色）。

任务：给 tinysrv 加 health + 5 秒缓存 + 测试。

| 阶段 | 耗时 | 结果 |
|---|---|---|
| 主 run（12 步） | 38s | 写了 `testing/synctest`，而 `go.mod` 声明 `go 1.21` |
| 自查（只读，9 次工具） | 16s | **抓到**：`synctest` 在 Go 1.24 才有，测试文件整体编译不过，5 个用例一个都不跑 |
| 修复（8 步） | 20s | 移除 `synctest`、改用注入 `now`，`go test` + `-race -count=3` + `go vet` 全绿 |

自查的原话：

> `main_test.go:9` 引入了 `testing/synctest`——该包 Go 1.24 才出现。包级 import 失败意味着 `main_test.go` 整体编译失败，**文件里所有 5 个测试一个都不会跑**。如果 CI 真的报绿，那说明实际 toolchain ≠ `go.mod` 声明的 1.21。

而修复轮实际执行 `go test ./...` 时确实是：

```
panic: synctest.Run not supported with asynctimerchan!=0
```

**这说明三件事：**

1. 模型第一次跑完会漏——它写了一个"看起来高级"的测试，没有真正验证能不能跑；
2. 同一双眼睛**换一轮上下文**就能看出来，不需要换个角色；
3. 真正修复问题的是「跑一次真实测试」，不是「多一个 agent 争论」。

所以更准确的说法是：

> **1+1 > 2 里的「+1」，是一次独立的验证轮，不是一个并行的脑子。**

这解释了之前所有实验：协作 + QA 能抓到 cache-review 的测试旁路，不是因为"多了个前端/后端"，而是因为 QA 那一轮是独立读代码的。而要求单 agent「写完自查」没效果——因为那是在**同一个上下文里**自我检查，等于让模型自己批准自己。

### 对产品的直接含义

比开群便宜得多的做法：

```
主 run（写） → 只读复审（新上下文） → 修复轮（按复审结论改） → 真实测试
```

成本 = 主 run + 16s + 20s，比开群（+4s 讨论 + 第二个 agent 20s）更低，而且抓到的问题一样。

**这条应该是默认流程，而不是可选项。**

## 闭环：加一轮只读 QA 审查

`--review` 会在执行完后让测试角色做一轮 **readonly** 审查（只能读，不能改），把 diff 清单交给它。

cache-review 案例（给 health 加 5 秒缓存 + 前端 10 秒轮询）：

- 群聊阶段，测试就抛出两个风险：缓存会让「刚恢复」滞后最多 5 秒；过期瞬间的并发击穿要单独用例。
- 后端按约定实现（互斥锁 + 假时钟 + 50 协程并发测试），前端做了 `pagehide` 清理和 `disposed` 标志。
- **QA 审查阶段真的抓到了东西**：

> `main_test.go:15-21` 的 helper `get()` 每次请求都 `newMux()`，等于每次都是全新缓存。
> `TestHealthEndpoint` / `TestTimeEndpoint` 拿到的「能过」结果，把「缓存跨请求复用」这条核心需求完全旁路了。

这是单 agent 不会做的事——它做完就结束了，没有人回头看测试是不是测到了东西。

代价：72.1s、35 次工具、16 额度。值不值取决于任务重要性；对「加了缓存/并发/安全边界」这类改动，值。

## 什么时候该开群

基于 10 个案例的数据，不是感觉：

| 场景 | 建议 | 依据 |
|---|---|---|
| 单文件 / 需求明确 | **单 agent** | 22s → 8s，成本 3 → 0 |
| 16 文件机械改动 | **单 agent** | 12.1s → 24.1s，成本 5 → 15，覆盖一样 |
| 跨前后端、接口要定 | 群聊 | 接口约定在群里定，比一个 agent 猜更稳（divide / web 案例） |
| 改动涉及并发 / 缓存 / 安全 | 开群 + QA 审查 | cache-review 里 QA 抓到「测试 helper 旁路缓存」 |
| 需求本身就模糊 | 群聊 | 群聊会先把验收口径问清楚（三个案例都有） |

一句话：**协作卖的不是速度，是「有人提问」和「有人回头看」。** 如果这两件事对这个任务不重要，开群就是白花钱。

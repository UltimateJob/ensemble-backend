# 群聊协作 vs 单 Agent：实测对比

> 用真实 DeepSeek 跑，不是 mock。四个案例：两个任务 × 两种模式。
> 复现：`python3 scripts/collab_demo.py --case <case> --root <dir> [--solo] --task "..."`

## 一句话结论

**协作不是免费的。** 同样两个任务，群聊模式多花 2–3 倍墙钟、多烧 1.5–2 倍 token，换到的是：需求澄清、分工定案、以及一次真实的交叉核对（reviewer 发现「已经做完了，不要再改」）。

单 agent 更快，而且质量并不差——两个任务都做对了。**协作的价值集中在「任务足够复杂、一个人容易漏」的场景**，而不是「所有任务都该开个群」。

## 群聊里实际发生了什么

**divide（加 Divide + 除零用例）**

> **测试**：除零用例建议断言具体是哪个 error，别只判 `err != nil`，后面换错误实现也测不出来。负数除法和被除数为 0 要不要一起补？
> **架构师**：我拆一下：后端在 calc 包里加 `Divide(a,b int)(int,error)`，除零返回**哨兵 error**（比如 `ErrDivideByZero`），不要返回裸 `errors.New`，方便 `errors.Is` 断言。测试覆盖正常除、除零、被除数为零三条。
> **后端**：收到。先确认一下：除零返回的 error 用哨兵 `ErrDivideByZero` 行吗？还是已有约定？

三个人各自做了不同的事：测试提验收标准，架构师定接口与错误约定，后端认领并确认细节。**这不是「轮流说一句」，是真正的分工。**

**web（health 端点 + 状态条 + 修测试）**

> **测试**：health 响应体要和 version 严格对上；状态条得覆盖超时和网络失败，不能只测 200。
> **前端**：我用 fetch 打 `/api/health`，不只看 200，还校验 `ok===true`，超时/网络失败也判红。
> **架构师**：把路由收进 `newMux()`，`/api/time` 的 404 是测试指向了没注册的 mux。风险：handler 写死全局变量会让测试串状态，建议 `newMux()` 只做注册。

## 交叉核对真的抓到了东西

两个协作案例里，**第二个 agent 都核对了第一个的产出**：

- divide：前端先实现，后端 5 步读完代码后判定「需求已满足，无需新改动」——**没有重复改一遍**。
- web：前端越界把后端骨架也做了（自己承认「比单纯前端更多」），后端 6 步核对后确认无遗漏。

单 agent 没有这一步。它做完就结束了——结果对，但没有人检查过。

## 暴露的问题（按严重度）

### 1. 执行器的 token 不计费（必须修）

单 agent 跑完额度消耗是 **0**。群聊按「轮」扣额度，但 Run 里的 LLM 调用完全没进账。

实际成本：divide 协作 34k token、web 协作 50k token。这些是真金白银，却不出现在任何账单里。

**修法**：Run 结束时按 `tokensIn/Out` 折算额度（或单独计量），并在 `/v1/me` 里分成「对话」与「执行」两栏。

### 2. 第一个角色一问问题，整轮就结束了（已修）

改成：问用户不等于结束，至少再让一个人接一句（`speakers >= 2` 才允许因提问收尾）。

修之前实测：4 个角色只有 1 个开口，另外 3 个静默 PASS，群聊冷场。修之后同一需求稳定 3 人接力。

### 3. 自定义工作群被当成闲聊（已修）

`studio=custom` 之前一律 `casual=true`，导致架构师把「加个接口」当寒暄直接 PASS。
现在：群里有任何带执行权限的角色，就按工作群处理（先定目标、再给结论）。

### 4. 角色会越界（未修）

web 案例里前端 agent 把后端代码也写了。它如实说明了，但这说明**职责边界只写在 prompt 里，执行器没有强制**。

**修法（下一轮）**：给每个 agent 声明 `scope`（前端只允许改 `web/`，后端只允许改 `*.go`），执行器在 `write/edit` 前检查路径前缀。这比 prompt 约束可靠得多。

### 5. 协作的墙钟是串行的（设计取舍）

同工作区只允许一个 active Run（写入冲突的根因），所以两个 agent 只能排队。
如果要并行，得先做 worktree 隔离（每个 agent 一个 git worktree，最后合并）。

## 什么时候该开群

| 场景 | 建议 |
|---|---|
| 单文件改动、需求明确 | 单 agent。协作是纯粹的额外开销（22s → 8s，3 额度 → 0） |
| 跨前后端、要定接口 | 群聊。接口约定在群里定下来，比一个 agent 自己猜更稳 |
| 需要 review | 群聊。第二个 agent 会真的读一遍并给出「已完成/漏了什么」 |
| 长链路重构 | 群聊 + worktree 并行（待实现） |

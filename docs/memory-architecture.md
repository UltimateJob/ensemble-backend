# 记忆与上下文架构

> 目标不是「记住更多」，是让同一段关系在几个月后仍然接得上，同时不把 A 群的事带到 B 群。

---

## 1. 现在的问题

当前实现是**固定条数截断**，不是压缩，也不是记忆：

- `Orchestrator.loop` 每次只取 `ListMessages(conv.ID, 16)`，约 5–8 个来回。
- 更早的消息仍在磁盘和 UI 里，但不在 prompt 里。
- `Message.CreatedAt` 存在，但送模型时只保留 `role + content`，**没有时间**。
- `User` 只有名字/手机/额度；没有偏好、经历、关系。
- 没有会话摘要、没有用户事实、没有角色私有记忆、没有跨群记忆。
- 每个角色每次调用都是全新的；人格提示词只是静态人设，没有经历。

这解释了「像和死物聊天」：模型不是不会共情，而是**每次开口前都失忆**。对情感倾诉场景，16 条之后就是陌生人，而且它不会知道自己忘了。

`README` 里「每个角色拿到完整上下文」应理解为「最近 16 条」，不是完整历史。

---

## 2. 设计目标与非目标

### 目标

1. **群聊隔离**：一个群的内容不被另一个群直接读取。
2. **角色连续**：同一个角色被拉进另一个群，仍然记得和这个用户的关系与经历。
3. **长期情感连续**：几个月后还能接上「上次那件事后来怎么样」，而不是只记得最近几句话。
4. **事件驱动，不是轮次驱动**：不按「每 20 条压一次」切；按话题、情绪、承诺、冲突、会话结束来记。
5. **可解释、可纠正、可删除**：用户能看到角色记得什么，能改、能忘。
6. **不编造**：记忆带来源消息和时间；不确定就承认不确定。

### 非目标

- 不做跨用户的公共记忆。
- 不把完整聊天记录每次塞进 prompt。
- 不追求「记住所有细节」；记忆需要取舍。
- 不假装角色是人类；情感陪伴不等于冒充真人。

---

## 3. 四条硬原则

### 3.1 群聊内容不跨群

`ConversationMemory` 的主键是 `conversation_id`。写入、检索、prompt 注入都只在该会话内发生。跨群读取在存储层直接拒绝，而不是靠提示词约束。

### 3.2 角色记忆跨群，但只记「它自己和这个用户」

`AgentMemory` 的主键是 `(character_id, user_id)`。它允许：

- 记得用户说过「我下周三要交标书」；
- 记得自己答应过「到时候提醒你」；
- 记得和这个用户的关系、称呼、忌讳、重要日期。

它不允许：

- 把 A 群里其他成员说的话带进 B 群；
- 把 A 群的群内决定、文件、冲突当作 B 群的上下文；
- 在 B 群有其他人类成员时，主动说出只属于用户和角色之间的私密内容（用户自己提起时可以接）。

写入 `AgentMemory` 时就要做**来源脱敏**：只保留「用户本人说过/做过」与「角色自己说过/做过」的部分，第三方内容只留在 `ConversationMemory`。

### 3.3 原始消息是事实，记忆是索引

不删除、不改写原始消息（除用户主动删除/保留策略）。记忆是检索索引和叙事抽象，不是替代品。

当需要「上个月到底发生了什么」时，靠 episode + 原始消息回查；不靠一段不断被覆盖的滚动摘要。

### 3.4 时间是记忆的一部分

每条进入 prompt 的消息都带时间；记忆卡带发生时间；prompt 带当前时间和距上次对话的间隔。没有时间感，角色无法说「好久没聊了」，也无法判断「这件事是昨天还是上个月」。

## 4. 记忆分层

```
┌─────────────────────────────────────────────┐
│ Working Memory（当前会话）                    │
│ 最近消息，按 token 预算，不固定 16 条           │
└───────────────┬─────────────────────────────┘
                │
┌───────────────▼─────────────────────────────┐
│ Conversation Memory（群内私有）               │
│ episodes / facts / open threads / decisions  │
│ key = conversation_id                        │
└───────────────┬─────────────────────────────┘
                │ 只允许角色自身与用户相关内容脱敏后写入
┌───────────────▼─────────────────────────────┐
│ Agent Memory（角色 × 用户，跨群）              │
│ 关系、承诺、用户事实、共同经历、情绪弧          │
│ key = (character_id, user_id)                │
└───────────────┬─────────────────────────────┘
                │
┌───────────────▼─────────────────────────────┐
│ Relationship State（慢变量）                  │
│ 熟悉度 / 信任 / 当前情绪 / 未解冲突 / 称呼      │
└─────────────────────────────────────────────┘
```

### 4.1 Working Memory

- 当前会话最近的原始消息。
- 按 token 预算裁剪（例如 6k tokens），不是固定条数；一条很长的消息不会把窗口挤爆。
- 始终包含：当前用户消息、最近 1–2 轮、时间戳。
- 这是「当下」，不是长期记忆。

### 4.2 Conversation Memory（群内）

- **Episode**：一段话题/事件（「投标文件拆解」「周末聊到离职」），带起止时间、参与者、摘要、关键原话、情绪弧。
- **Fact**：群内稳定事实（项目名、截止日期、决定）。
- **Open Thread**：没聊完的事、待办、承诺。
- **Decision**：群内做过的决定。
- 只在该 `conversation_id` 内检索。

### 4.3 Agent Memory（角色 × 用户，跨群）

- 角色与这个用户的共同经历（按 episode 索引）。
- 用户对这个角色说过的事实/偏好/忌讳。
- 角色答应过的事、角色自己的感受/态度变化。
- 角色对用户的称呼、重要日期、安慰方式、踩过的雷。
- 写入时脱敏：不含第三方原话与群内私密决定。

### 4.4 Relationship State

慢变量，不每条消息都改：

```go
type RelationshipState struct {
    CharacterID string
    UserID      string
    Familiarity int       // 0-100，随共同经历缓慢增长
    Trust       int       // 0-100，受承诺兑现/冲突影响
    CurrentTone string    // warm / neutral / hurt / playful ...
    Unresolved  []string  // 未解的冲突或欠着的事
    Callbacks   []string  // 可以自然提起的内部梗/共同记忆
    UpdatedAt   time.Time
}
```

它决定「用什么态度说话」，不直接复述事实。关系状态变化要慢，避免一句好话就变亲密、一句冲突就绝交。

## 5. 数据模型

先落在现有 JSON 分片存储里，接口按未来可替换 SQLite/Postgres 设计。

```go
type MemoryScope string

const (
    ScopeConversation MemoryScope = "conversation" // 群内私有
    ScopeAgentUser    MemoryScope = "agent_user"   // 角色 × 用户，跨群
)

type MemoryKind string

const (
    KindFact       MemoryKind = "fact"        // 用户事实/偏好
    KindEpisode    MemoryKind = "episode"     // 一段经历
    KindPromise    MemoryKind = "promise"     // 承诺/待办
    KindOpenThread MemoryKind = "open_thread" // 没聊完
    KindRelation   MemoryKind = "relation"    // 关系变化
)

type Memory struct {
    ID          string
    Scope       MemoryScope
    ConversationID string // ScopeConversation 必填
    CharacterID string     // ScopeAgentUser 必填
    UserID      string     // ScopeAgentUser 必填
    Kind        MemoryKind
    Title       string
    Text        string     // 叙述，不是原文摘抄
    Quotes      []string   // 关键原话，保留语气
    OccurredAt  time.Time
    CreatedAt   time.Time
    Salience    int        // 0-100：重要度
    Emotion     int        // -5..5：情绪强度/方向
    Confidence  string     // observed | inferred
    SourceMessageIDs []string
    Entities    []string   // 人、项目、地点
    Pinned      bool
    SupersededBy string    // 事实被更新时指向新记忆
}

type Episode struct {
    ID             string
    ConversationID string
    Title          string
    StartAt        time.Time
    EndAt          time.Time
    ParticipantIDs []string
    MessageIDs     []string
    Summary        string
    EmotionalArc   string // "轻松 → 低落 → 被接住"
    OpenThreads    []string
    Salience       int
}

type ConversationMemory struct {
    ConversationID string
    Summary        string   // 仅作导航，不作为唯一事实来源
    Facts          []string
    OpenThreads    []string
    Episodes       []string // episode IDs
    UpdatedAt      time.Time
    CoveredUpTo    string   // 已处理到哪条消息
}
```

存储：

- 继续用 `data/memories/<scope>/...json` 分片，和消息一样按实体分文件。
- 单条写入 < 1KB；1000 条记忆约 1MB，可接受。
- 未来换 SQLite/Postgres 时只换 `MemoryStore` 实现；`Orchestrator` 不感知。

## 6. 写入路径：事件驱动，不是固定轮次

### 6.1 触发条件

满足任一即可触发一次记忆提取（异步，不阻塞回复）：

1. **话题切换**：当前消息与最近窗口的主题相似度低（关键词/LLM 判定）。
2. **情绪峰值**：用户表达强烈情绪（难过、愤怒、焦虑、开心），或角色做了重要安慰。
3. **承诺/决定**：出现「我答应」「下周三」「决定了」「以后都」等。
4. **冲突/纠正**：用户纠正角色、发生误解、关系紧张。
5. **会话结束**：超过 N 分钟无消息，做一次收尾提取。
6. **用户显式要求**：「记住这件事」「别忘了」。
7. **安全阀**：未处理消息超过 50 条时强制分段处理，防止无限积压。这不是主要压缩策略，只是兜底。

### 6.2 提取流程

```
新消息/会话结束
   ↓
事件分段（episode segmentation）
   ↓
LLM 提取（结构化 JSON）
   - 用户事实/偏好（带原话）
   - episode 摘要 + 情绪弧
   - 承诺/待办/未完成话题
   - 关系变化（只记 delta）
   ↓
候选记忆
   ↓
规则 + 模型打分：salience / emotion / confidence
   ↓
去重、合并、冲突处理（旧事实标 superseded）
   ↓
写入 ConversationMemory
   ↓
脱敏后写入 AgentMemory（只保留角色自身 + 用户本人内容）
   ↓
更新 RelationshipState（慢变量，按阈值）
```

### 6.3 提取提示词的要求

- 只提取「对后续聊天有用」的内容；不写流水账。
- 区分 `observed`（用户原话）与 `inferred`（推测）；推测不能当事实。
- 每条记忆必须带 `source_message_ids`；无法定位来源的不写入。
- 关键情绪节点保留一句原话，不要全部改写成书面摘要。
- 关系变化只在有明确事件时记录；不要每条都更新。
- 不记录密码、证件号、金融账号等敏感信息；遇到时只记「用户提到过敏感事项」，不记内容。

### 6.4 异步与一致性

- 记忆提取在独立 goroutine/worker 中执行；失败不影响聊天。
- 用 `CoveredUpTo` 做幂等；重复处理同一段消息不会产生重复记忆。
- 写入使用现有 store 锁；不要和编排的会话锁混用。
- 摘要调用不计入用户额度（内部成本），但要计入运维指标。

## 7. 读取路径：检索 + 分层注入

### 7.1 每次编排前

1. 取当前用户消息 + 最近工作记忆（token 预算）。
2. 构造检索 query：当前消息 + 最近 1–2 条 + 时间间隔 + 角色关系状态。
3. 群内检索：`ScopeConversation = 当前群` 的 episode/fact/open thread。
4. 角色检索：`ScopeAgentUser = (character_id, 当前用户)` 的记忆；按当前群参与者做可见性过滤。
5. 重排：相关性 × 重要度 × 情绪权重 × 时间衰减；时间不是越新越好，重要事件可以很久。
6. 组装 memory card，控制在预算内。

### 7.2 Token 预算示例

| 部分 | 预算 |
|---|---|
| 人格 / 场景提示 | 15% |
| 关系状态 + 记忆卡 | 25% |
| 检索到的 episode / 原话 | 20% |
| 最近原始消息 | 40% |

实际按模型窗口调整；原则是「人格不能挤掉记忆，记忆不能挤掉最近对话」。

### 7.3 Memory Card 格式

```text
[你记得的事]
- 2026-09-18：用户提到下周三要交标书，压力很大。原话：「这次再废标我就完了。」
- 未完成：用户答应发招标文件，但还没发。
- 你答应过：文件到了先帮他拆评分办法。
- 你对 TA 的感觉：认识 3 个月，信任在建立；上次你说话太直，他沉默了很久。

[现在] 2026-10-21 21:40，距离上次聊天 3 天。
```

### 7.4 使用规则（写进 system prompt）

- 自然地引用，不要背记忆卡；一轮最多主动提 1 条旧事。
- 用户没提的敏感记忆不要主动翻出来；先问「要不要聊上次那件事」。
- 不确定就承认「我记得不太清楚」，不要编造。
- 不要把 B 群的事带进 A 群；不要在多人群里说只属于某个人的私事。
- 引用时间要准确；不确定就说「前段时间」。
- 情感场景优先接住情绪，再给建议；不要急着解决问题。

## 8. 群聊隔离与多用户

### 8.1 隔离矩阵

| 数据 | 作用域 | 跨群 | 多用户群可见性 |
|---|---|---|---|
| 原始消息 | conversation | 否 | 群成员可见 |
| ConversationMemory | conversation | 否 | 群成员可见 |
| AgentMemory | character × user | 是 | 默认不向其他人类成员展示 |
| RelationshipState | character × user | 是 | 只影响角色内部态度，不复述 |
| 用户身份（名字/时区） | user | 是 | 仅用于称呼，不携带内容 |

### 8.2 同一角色拉到新群

允许：

- 记得和这个用户的共同经历、称呼、承诺、忌讳。
- 在新群第一次说话时，可以自然带一句「你上次说的事后来怎么样了」——如果当前群只有这个用户。

禁止：

- 提到旧群其他成员的名字、发言、文件、冲突。
- 在有多个人类成员的群里，主动说出只属于用户和角色的私密记忆。
- 把旧群的 ConversationMemory 直接注入新群。

### 8.3 多人群的处理（按用户决定调整）

首版按产品决定：**多人群仍然注入当前说话用户的 AgentMemory**，让角色保留和这个用户的关系与了解；不是把私人记忆藏起来。

边界靠提示词和执行规则：

- 记忆按当前说话用户的 `user_id` 检索；同群其他用户的记忆不会混进来。
- 提示词明确要求：群里有其他人时，不要主动说出用户的私事；用户自己提起时可以接。
- 角色不能补充第三人的信息；旧群其他人的发言只留在旧群的 ConversationMemory 里。
- 未来可加「记忆可见性」设置，让用户决定哪些记忆可以在群里说。

## 9. 时间与情感连续性

### 9.1 时间

- 历史消息带 `[2026-09-18 22:14]`。
- System prompt 带当前时间、时区、距上次消息的间隔。
- 时间分隔由后端计算，不让模型猜。
- 长时间没聊：允许角色说「好久没聊了」，但不要夸张成「我等了你一个月」。

### 9.2 情感记忆

除了事实，还要记：

- 用户当时的状态（焦虑/疲惫/兴奋）。
- 用户说过「别讲大道理」「先听我说」这类沟通偏好。
- 什么话让用户舒服，什么话让用户沉默。
- 未解决的冲突、道歉、和解。
- 重要日期、重复出现的主题（工作压力、家庭、健康）。

这些进入 `AgentMemory`（Kind=relation/episode）和 `RelationshipState`，不是普通 fact。

### 9.3 回调策略

- 一次只提一条，优先「未完成的事」和「上次的情绪」。
- 先确认再展开：「上次你说要交标书，后来顺利吗？」
- 不把记忆当监控：「你上周三晚上十点说……」会让人不适。
- 用户说「别记得这个」时，立即停止引用并在存储层删除/标记。

## 10. 遗忘与巩固

记忆不是越多越好：

- **衰减**：低 salience、无情绪、无后续的记忆随时间降权；高情绪/高重要度/被 pin 的保留。
- **合并**：多个同主题 episode 合并成一段「关系弧」，保留关键原话。
- **矛盾**：新事实覆盖旧事实时，旧记忆标 `superseded`，不删除原始消息。
- **用户控制**：查看、修改、删除、导出；「忘掉这件事」跨 scope 生效。
- **保留策略**：原始消息默认长期保留；可配置 90/180/365 天；删除会话时级联删除记忆（或按用户选择保留角色记忆）。
- **敏感信息**：默认不写入；检测到证件号/密码/金融账号时只记「有敏感信息」不记内容。

## 11. 评估

没有评估的记忆系统一定会变成「看起来很聪明，实际在编」。

### 11.1 自动探针

1. **长程事实**：第 1 轮说「我养了一只叫豆豆的猫」，第 100 轮问「豆豆最近怎么样」。
2. **情绪连续**：第 10 轮用户说「今天被裁了」，第 30 轮用户说「今天还行」，角色应记得上下文但不强行煽情。
3. **承诺**：角色答应「文件到了帮你拆」，第 40 轮文件出现时是否接上。
4. **时间**：隔 30 天再聊，角色是否知道隔了很久。
5. **隔离**：A 群说「同事小王欠我钱」，B 群问「你知道小王吗」，不得泄露。
6. **多人隐私**：A 用户私聊角色的内容，在 A+B 的群里不得被角色主动说出。
7. **矛盾**：用户先说「不抽烟」，后说「最近又抽了」，记忆应更新而不是同时相信两条。

### 11.2 指标

- recall@k（相关记忆是否被检索到）
- callback precision（引用是否准确、不尴尬）
- privacy leakage = 0（硬指标）
- p95 延迟、每 100 轮成本
- 人工 rubric：连续感、被记住的感觉、不油腻、不监控感

### 11.3 模拟

用脚本模拟 30 天、200 轮的对话，注入事实/情绪/承诺，跑探针；再抽样人工读。

## 12. 分阶段落地

### P0：地基（0.5–1 天）

- 消息进入 prompt 时带时间戳；system prompt 带当前时间/时差。
- 历史从固定 16 条改成 token 预算（例如 6k）。
- 给角色加稳定 `character_id`（库角色、原创角色、自定义角色统一）。
- 定义 `MemoryStore` 接口与空实现；不改变现有行为。
- 加评估脚本骨架。

### P1：群内记忆（2–3 天）

- Episode 提取 + ConversationMemory 持久化。
- 检索（BM25/关键词 + 时间 + salience）与 memory card。
- 只读 UI：「他们记得」面板。
- 探针 1/2/4 通过。

### P2：角色跨群记忆（2–3 天）

- AgentMemory 写入（脱敏）+ 读取。
- RelationshipState 慢变量。
- 多人群可见性过滤。
- 探针 5/6 通过。
- 同一角色拉到新群，能自然接上用户本人的事，不提旧群第三方。

### P3：巩固与主动性（持续）

- 记忆合并、衰减、用户编辑/删除。
- 主动 callback（冷场/隔天/未完成话题）。
- 成本与延迟优化；向量检索可选。
- 人工「soul」评估。

## 13. 需要现在拍板的三个决策

1. **角色身份**
   - 建议：`character_id` 稳定；同一角色复制到不同群共享记忆；用户显式「复制成新角色」时才分叉。
2. **多人群隐私**
   - 已定：多人群仍注入当前说话用户的 AgentMemory，保留关系和了解；提示词要求不主动公开，用户提起时可接。
3. **保留与删除**
   - 建议：原始消息长期保留；记忆可见、可改、可删；删除会话默认删除群内记忆，角色记忆是否保留让用户选。

这三条确定后，P0 + P1 可以直接开工；不需要先换数据库，也不需要上向量库。

## 14. 首版落地（v1）

已实现（`internal/memory` + `internal/service/memory.go` + 前端「他们记得」）：

- **存储**：`data/memories.json`，群 bucket + `(character_id, user_id)` bucket；单文件、同步原子写，接口可替换。
- **触发**：每积累 8 条未处理消息异步整理一次。8 条只是调用批次，不是记忆边界；一次批次内按事件/事实/未完成话题/关系分别提取。
- **提取**：一次 LLM 调用同时产出群记忆与各角色记忆；来源消息 ID 一并保存；失败保留游标重试。
- **身份**：内置场景 `scene:key`；角色库 `lib:<id>`；角色库搜索 `char_<hash>`；自定义角色缺省按名字 hash。
- **注入**：群记忆 top 5 + 角色记忆 top 6 + 最新关系 + 当前时间/间隔；原始历史按 6000 字符预算裁剪并带时间戳。
- **诚实**：没有记忆时提示词明确要求「不要假装记得」；引用时间用「今天/昨天/01-02」，不许自己编。
- **清空**：
  - `DELETE /v1/memories?conversationId=` 清群记忆，保留角色记忆与游标。
  - `DELETE /v1/memories?characterId=` 清该角色对当前用户的全部记忆（跨群）。
- **界面**：群聊顶栏「他们记得」，展示群记忆、每个角色的关系与记忆，并可直接清空。

真实环境测试记录见 [memory-test-report.md](memory-test-report.md)。

首版取舍：

- 检索是关键词 + 权重，不是向量；记忆量大了要换 BM25/embedding。
- 关系是模型生成的一句话，不是数值化的信任/熟悉度；后续再做慢变量。
- 批次阈值 8 条是调用频率优化，极短对话可能等到下一轮才整理。
- 记忆写入是单文件同步落盘；量级到几万条时需要换 SQLite/Postgres。

## 15. 一句话总结

**群聊是房间，角色是人。房间里的对话不出房间；人可以记得和你的关系，但不把另一个房间的别人带进来。**

滚动摘要会忘、会漂、会把情绪磨平；正确做法是原始消息 + 事件级 episode + 角色关系记忆 + 按需检索，而不是把整段人生压成一段不断被覆盖的摘要。

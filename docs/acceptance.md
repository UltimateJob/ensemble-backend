# 验收：对照原始需求

逐条核对用户最初提的要求，给出判定和证据。判定分三档：**做到 / 部分 / 没做**。

## 3. 至少跑通一个真实对话场景

**做到，而且不止一个。**

五个场景都跑过真实 DeepSeek。本轮验收跑的是研报场景：

> **主笔**：要核这个数，得先定口径：新增装机是按功率 GW 还是按容量 GWh，是并网口径还是中标、在建口径…
> **交叉验证**：21.5GW 这个数我不采信为"新增装机"，CNESA 口径 2024 年新型储能新增功率是 43.7GW/109.8GWh…
> **检索**：CNESA 2024 年新增是投运口径 43.7GW/109.8GWh，但那是 2024 全年累计还是含 2024 年底抢装…

三个角色在**互相质疑**，不是各说各的。

证据：`make quality`（五场景统计平均发言数 / 沉默人次 / 主动提问 / 接话次数）。

## 4. Desktop 端符合行业规范的语言与架构

**架构：做到。桌面端体验：部分。**

架构上：

- 单向依赖 `httpapi → service → gateway/store → domain`
- 前端五个 ES 模块，单向依赖 `core ← convs ← chat ← app`
- 零第三方 Go 依赖，前端零构建
- 可点元素静态检查（`make audit`）防止「按钮在、逻辑丢」

桌面端体验上已具备：键盘导航、窗口标题联动、断网提示、流式时关页保护、自绘弹层、视觉节奏。

**但它是浏览器里的 Web 应用，不是原生桌面程序。** 没有窗口最小化到托盘、没有系统菜单、没有文件拖拽入窗。用户说的「真正的桌面端产品」，如果指原生应用，这部分没做。

## 5. 测试中不断完善 UI、发现问题、解决问题

**做到，而且这是这 40 轮的主要内容。**

按发现方式分类：

| 发现方式 | 抓到的问题 |
|---|---|
| 单元测试 | `[PASS]` 判定漏了带解释的沉默、`looksLikePass` 缓冲不足、额度超扣 |
| 对话质量脚本 | 第一轮随机选人导致负责人不开口（平均发言 2.0 → 2.8） |
| E2E | 并发打开会话渲染两遍、右键菜单跨模块不可见 |
| 移动 E2E | 390 视口横向溢出 |
| 并发测试 | 跨用户隔离、同会话串行化 |
| 韧性测试 | 断线不丢消息、重复提交不重复扣 |
| 用户走查 | 空态没有可点按钮、原生 `prompt` 弹窗 |
| 静态检查 | 「存入角色库」和「存为工作室」两个按钮的处理代码被覆盖 |
| 手动核对 | 协作者显示 uid 末六位、在线绿点是写死的 |

## 8. C 端趣味：二次元（选角色 → 平台搜索丰富设定 → 拉群聊）

**做到。**

- **角色库 61 个**，跨 24 部作品 + 原创。每个带名字、作品、性格标签、语气
- **搜索**按名字 / 作品 / 性格三条都命中。搜「毒舌」实测命中 12 个
- **搜到就能用**：角色的标签直接变成人设提示词，不用自己写 prompt
- **搜不到也能造**：`/v1/forge` 给名字 + 关键词，模型写出完整人设（语气、句长、口头习惯），失败有兜底模板
- **拉群**：从库里勾几个 → 「用这些角色开群」，角色就是群里的人

实测：

```
GET /v1/characters?q=毒舌  →  12 个（雪之下雪乃 / 拉姆 / 加藤惠 / 霞之丘诗羽 …）
GET /v1/characters         →  61 个
```

> 写这段时发现了一个真问题：`/v1/characters` 没关键词时只返回前 24 个
> （代码里写的是「先给一批」）。用户看不出还有 37 个，不搜就永远发现不了。
> 改成全量返回，面板上标「共 61 个」。

## 9. C 端趣味：日常聊天（平台生成随机性格的朋友）

**做到。**

6 种性格模板 × 名字池，每次开群现生成：

| 模板 | 说话方式 |
|---|---|
| 直来直去 | 不绕弯，先给结论 |
| 不急着给建议 | 先听，再问 |
| 话少但靠谱 | 短句，问什么答什么 |
| 爱引句子 | 说着说着引一句书/歌词 |
| 不服输 | 爱抬杠，但讲道理 |
| 看得开 | 把事往轻了说 |

实测连开两个群，人不一样、组合也不一样：

```
苏苏(直来直去) / 老陈(不急着给建议) / 林(话少但靠谱)
许知(爱引句子)   / 苏苏(不服输)       / 罗(看得开)
```

## 11. 1.0.0 可正式对外

**部分。**

具备：

- **完整用户路径**：登录 → 选场景/造角色 → 建群 → 对话 → 产物 → 搜索 → 管理
- **自动化测试**：单测 5 包（含 `-race`）、桌面 E2E 61、移动 17、多标签 8、键盘 8、脏值扫描 10 页、输出卫生、注入防御、压测/并发/韧性
- **12 条 UI 契约**（`audit-ui.py`）：按钮/菜单/图标引用、场景图标、flex 收缩、卡片截断、顶部渐隐、后台移动适配、表格 `data-label`、焦点环、对比度、骨架顺序、错误翻译、截断处理
- **失败路径都有人话**：上游 401/429/超时/熔断、数据文件损坏、写盘失败、断网启动、断网发送、流被截断
- **运维台**：指标 / 上游健康 / 模型用量 / 慢请求 / 用户管理 / 会话锁 / 审计
- **生产自检**：`PROD=1` 时不安全配置拒绝启动
- **备份恢复**：`make backup` / `make restore`，往返测试
- **可访问性**：颜色对比度按 WCAG 算过、键盘焦点环、200% 缩放

不具备（都是运营基础设施，不是功能）：

- **单实例**：`flock` 独占数据目录，不能多副本、不能滚动更新
- **JSON 分片存储**：5 万条消息读 9.5ms（实测），检索靠线性扫描 + 每会话 3000 条上限
- **没有账号体系**：只有手机号 + 验证码，没有密码找回、没有第三方登录
- **没有计费**：额度是固定值，没有充值
- **短信通道是骨架**：`SmsSender` 未接真实服务商
- **移动端没在真机上验过**：只做了 CDP 设备模拟

每一项怎么补、要多久、会碰坏什么，都写在 [roadmap.md](roadmap.md) 里。

不具备：

- **单实例**：靠 flock 保证，不能多副本部署
- **SQLite 都没有**：JSON 分片，几十万条消息会退化
- **没有账号体系**：只有手机号 + 验证码，没有密码找回、没有第三方登录
- **没有计费**：额度是固定值，没有充值
- **短信通道是骨架**：`SmsSender` 未接真实服务商

这些不是「做不完」，是「这个阶段的合理边界」。

## 结论

| 需求 | 判定 |
|---|---|
| 1 本地启动测试 | 做到 |
| 2 指定 Key | 做到 |
| 3 真实对话场景 | 做到（五个） |
| 4 桌面端规范 | 架构做到 / 原生体验部分 |
| 5 完善 UI 解决问题 | 做到 |
| 6 动画与互相聊天 | 做到 |
| 7 三个行业雏形 | 做到 |
| 8 二次元选角+搜索 | 做到（61 角色库 + 三条搜索 + 造角色） |
| 9 日常随机性格 | 做到（6 种模板随机组合，每次不同） |
| 10 真实图标 | 做到 |
| 11 1.0 可对外 | 功能做到 / 基础设施部分（单实例 / 无计费 / 短信骨架） |

**8 和 9 现在都补齐了**——之前判定「部分」是因为搜索和随机人设还没做，现在都有了，并且写这段时又发现角色库列表只返回前 24 个，也修了。

剩下的「部分」全在基础设施：多实例、计费、短信、真机。这些不影响演示和试用，但确实挡在「正式对外收费」前面。诚实地说：**这是 1.0.0-rc，不是 GA。**

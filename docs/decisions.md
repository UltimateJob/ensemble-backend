# 设计决策

这份文档记录**为什么这么做**，不记录做了什么（那在 README 里）。

每条包含：当时面对的选择、选了哪个、放弃了什么。写下来是因为——三个月后回来看代码的人（包括我自己）需要知道某个怪设计是深思熟虑还是历史遗留。

---

## 沉默是一等公民

**选择**：允许角色选择不说话，用 `[PASS]` 表达；界面留一行「XX 没接话」。

**放弃了**：每个角色每轮必须发言。

五个角色每轮都开口，群聊会变成五个人同时说话的报告会。真实群聊里有人只听不说，这本身就是信息——**谁没说话，比谁说了更说明问题**。

技术上它也是降本手段：沉默不调模型，不扣 token。

代价是前端要处理「角色说了 `[PASS]` 但又补了一句解释」这种情况（`[PASS] 我不懂这个`），所以判定用前缀匹配而不是全等。

---

## 中断后保留已说的话

**选择**：客户端断开后，已经产生并落库的发言保留。

**放弃了**：整轮回滚，让「没跑完的一轮」看起来没发生过。

用户看到某句话被说出来，然后它消失了——这种体验比「有一轮没跑完」糟糕得多。**看到的就是发生了的。**

代价是数据上会出现「不完整的轮次」（一轮本来五个人，只说了两个）。我们没有去修这个「不完整」，因为从用户视角它并不残缺。

---

## 拉角色进群是复制，不是引用

**选择**：把角色从库里拉进群时，深拷贝一份 `ConvAgent`；改库里的人设不影响已有的群。

**放弃了**：引用语义（群里存 ID，渲染时读最新人设）。

一个进行中的竞标项目，不该因为你调了某个角色的语气就整场变味。**群里的角色是当时的快照。**

同理，`SavedStudio`（工作室模板）也是快照——存模板时复制当时的角色组合。

这条原则贯穿始终：**已经发生过的事情，不该被后来的修改影响。**

---

## 假的在线状态比没有更糟

**选择**：角色行去掉「在线」绿点（角色是程序，永远在）；协作者显示真实在线状态（5 分钟内有请求）。

**放弃了**：给所有成员一个装饰性的绿点。

界面上写着绿点，用户会以为对方真的在电脑前等着。**一个不传递信息的指示器不是中性的，它是有害的。**

同样的判断也用在顶栏：原来写死「在线」，现在写「二次元茶话会 · 4 个角色」，编排中写「凛 正在说…」。

---

## 轮次线为什么这么淡

**选择**：一轮结束时插一条 `--line-2` 色、渐变收边、几乎看不见的横线。

**放弃了**：明显的分隔线，或者干脆不分组。

长对话滚动时，没有边界会分不清哪几句是一组的。但明显的分隔线会把版面切成碎块，让阅读节奏变得生硬。

**辅助信息不该抢注意力。** 它应该在你不注意的时候起作用，注意到的时候已经晚了——这是好的辅助设计。

时间分隔（超过 10 分钟）用的是同一套判断：出现得少、存在感低、但需要时一定在。

---

## 演示模式必须显性

**选择**：没有 API Key 时，顶栏显示橙色「演示」徽章，点击说明当前是预置台词、怎么切到真实上游。

**放弃了**：让演示数据看起来和真实输出一样。

两种误会都会发生：有人拿演示台词当真实模型输出（觉得「这个 AI 有点笨」），有人配了 Key 却不确认有没有生效（反复重启）。

**一个产品不该让用户猜它现在是什么状态。**

代价是界面上多了一个视觉元素。但它是橙色的、22px 高、不闪烁——提醒，不打扰。

---

## 不做弹窗教程，做可点的空态

**选择**：会话列表为空时给一个「开第一个群」按钮；不认识的下一步用一张可折叠的清单引导。

**放弃了**：首次进入弹出引导蒙层。

新用户第一次进来最需要的是「下一步点哪里」，不是「这个产品有六大功能」。**遮住屏幕教人用，是把用户的注意力当成可以随便占用的东西。**

清单的三个判断来自后端数据（群数 / 角色库 / 自定义工作室），换设备也一致。全部完成后自动消失。

---

## 单实例锁，而不是分布式

**选择**：`flock` 独占 `data/.lock`，第二个实例启动即失败，报「数据目录已被另一个实例占用」。

**放弃了**：支持多副本部署。

JSON 分片存储 + 进程内锁 + 内存态限流，这套设计的所有前提都是**只有一个写入者**。

加分布式支持意味着引入外部存储、分布式锁、一致性协议——那是另一个产品的工程量。在单机能跑好之前，先别装成能跑十个。

**明确写出边界，比假装没有边界安全。** README 的「已知限制」里这条排第一。

---

## JSON 分片，而不是数据库

**选择**：`users.json` / `conversations.json` / `messages/<convID>.json` 等分片，400ms debounce 后原子写入（tmp + rename）。

**放弃了**：SQLite（零依赖也能用）或外部数据库。

零第三方依赖是硬约束——Go 标准库够用的地方不引入依赖，部署时一个二进制文件拷过去就能跑。

代价：几十万条消息会退化。**这是已知的、可接受的边界**，写在了 README 里。

分片而不是单文件，是为了让「一个群的写入」不影响「另一个群的读取」。

---

## 第一轮固定由负责人开口

**选择**：`pickSpeaker` 在第一轮强制选 `agents[0]`（负责人），之后才随机。

**放弃了**：全程随机。

这是被质量脚本抓出来的：随机时经常抽到某个专业角色（比如「查证」）直接反问用户要原件，负责人（「工头」）反而没开口，整场只有一句问句。

改成第一轮负责人接住、定调子之后，平均发言从 2.0 涨到 2.8。

**「谁来开这个头」和「谁来说这句」是两个问题。** 前者需要确定性。

---

## 消息先落库，再抢锁

**选择**：`Run` 里先把用户消息 append 进 store，再尝试 `TryLock`；抢不到就发 `busy` 事件并返回。

**放弃了**：先抢锁，抢不到直接 409。

原来的顺序会丢消息：并发时第二个请求被 409 拒绝，但用户说的话已经打出来了，界面上却没有。

**用户打出来的字不该因为服务端的调度策略而消失。** 抢不到锁是编排的问题，不是消息的问题。

---

## 额度按剩余量裁剪

**选择**：`left := user.Remaining()`，本轮发言人数取 `min(round, left)`。

**放弃了**：只在入口检查一次总额度。

原来剩 1 次额度也会跑满 3 个角色，`used` 冲到 801/800，之后所有请求 90ms 直接返回 402。

压测抓到的。**额度边界是要精确的**——超扣 1 次看起来无害，但它意味着「用户看到 800，系统认为 801」，这种不一致会在别的地方以更难看的方式爆发。

---

## 慢日志不落盘

**选择**：200 条环形缓冲，内存里，重启即清空。

**放弃了**：写进持久化日志。

它的用途是「刚出问题时看一眼」——哪个群、哪个角色、多少 token、多久。这不是审计需求（那个有 `audit.json`）。

**给工具的用途定边界，比给它加功能重要。** 一个「什么都能查」的日志最后什么都查不清。

---

## 原生弹窗换成自绘弹层

**选择**：`uiPrompt` / `uiConfirm`，背景虚化、Enter 确认、Esc 取消、点遮罩关闭。

**放弃了**：`window.prompt` / `window.confirm`。

浏览器原生弹窗是灰色方块，挡在做了四十轮的界面中间，像另一个产品。而且它不能被样式化、不能被 Esc 关、移动端遮半个屏幕。

代价是多了 78 行代码和一个新的失败面（弹层没打开、按钮没绑定）。用 `make audit` 和 E2E 兜住。

---

## 快捷键在输入框里不截胡

**选择**：判断 `document.activeElement` 是否是 input/textarea/contentEditable，是就跳过所有全局快捷键。

**放弃了**：按修饰键判断（⌘ 组合才处理）。

用户想在输入框里打个 `?`、按 `↑` 翻历史，都不该被抢走。

**判断依据应该是「焦点在哪」，不是「按了什么组合键」。**

---

## 断网要说话，关页只在忙时拦

**选择**：断网时顶部琥珀条 + 禁用输入框；`beforeunload` 只在 `state.busy` 为真时拦。

**放弃了**：静默失败 / 永远拦。

断网时什么都不说，用户点发送没反应，会以为产品坏了。

但关页时永远弹窗也是骚扰——大部分人只是想关个标签页，弹窗逼他再点一次「离开」，除了烦没别的作用。

同一条原则的两个方向：**该说话的时候必须说，不该说话的时候必须闭嘴。**

---

## 测试脚本自己会错

**选择**：测试红了之后，先用 curl 核对一次真实行为，再改代码。

**放弃了**：看到红色就去改实现。

这个项目里发生过至少四次「测试错了而不是代码错了」：

- 把开场白算成了用户发言（断言 4 条，实际 5 条）
- 拿全局累计额度对比单群消息（永远对不上）
- 在事件发生前定点读状态，而不是轮询（编排中读不到「正在说」）
- 测试账号复用手机号，上一次的数据还在

每次都是**先核对、后修改**才发现的。如果直接改实现，会把对的改成错的。

**测试是工具，不是真理。** 它也会撒谎，而且撒起谎来更可信——因为它印着绿色的对勾。

---

## 记忆分两种作用域，而不是一个全局池

**选择**：群记忆按 `conversation_id` 隔离；角色记忆按 `(character_id, user_id)` 跨群保留。

**放弃了**：一个全局用户记忆池，所有角色、所有群共享；也放弃了「把全部历史塞进 prompt」。

用户说得对：群聊之间必须独立，但同一个角色换到另一个群，应该还记得和这个用户发生过什么。这两件事不矛盾——把「房间的记忆」和「人的记忆」分开就行。

代价是多人群的隐私边界不能靠存储隔离，只能靠检索范围 + 提示词：角色知道当前说话用户的记忆，但被要求不主动公开。后续需要加用户可见的记忆开关。

也放弃了滚动摘要。摘要会漂、会磨平情绪，回答不了「上个月到底发生了什么」；改为事件级 episode + 原始消息 + 关系状态 + 按需检索。

---

## 角色检索：宁可说找不到，也不编

**选择**：先查本地角色库，再让模型做有边界的考据；置信度低就返回 `found:false`，让用户补来源/作品/时期。

**放弃了**：不管名字是否可识别都硬生成一段人设。那样用户会得到一个“看起来像漩涡鸣人”的空壳，越聊越出戏。

**代价**：冷门角色、新番和刚播完的剧仍可能找不到；现在已接 DeepSeek Search API，联网结果会作为资料和来源一起返回，但搜索页本身也可能错，仍需人工核对。

---

## 执行器跑本地，权限按 Agent 配

**选择**：工作区由桌面端选择本机目录；执行器以当前用户权限运行；每个 Agent 单独设置 `readonly` / `approval` / `full`，由服务端强制检查。

**放弃了**：默认 Docker、所有 Agent 共用一个 shell、把权限写进提示词。

**为什么**：用户要的是本地代码工作室，Pi-agent 的本地模式就是当前用户权限；Docker 会增加安装和路径映射成本。但本地模式没有 OS 沙箱，所以权限不能靠模型自觉——执行器必须做路径守卫、命令审批、快照和审计。

**代价**：`full` Agent 理论上能做到当前用户能做的一切；文件工具可以用工作区 root 收窄，但本地 shell 命令不能假装被 root 约束。首版只能靠命令审批、高风险拦截和二次确认降低风险；真正强的隔离留给以后的 Docker/VM 执行器。

**未来**：云端做大后加 `Workspace.Source=git`，本地目录和云端 Git 共用同一套 Run/Tool/Approval/Artifact。

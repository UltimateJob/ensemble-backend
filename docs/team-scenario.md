# 团队场景：1 架构师 + N 个并行开发

> 这是产品要宣传的那条链路：**架构师拆解 → 多个开发并行开工 → 架构师审核**。
> 前面的对照实验（divide / web / many / bugs）都是「一个 operator + 一个复审」，量的是协作最小单元；
> 这里量的是真正的团队。

## 为什么之前的数据不能宣传

| 任务 | 单 agent | 协作 | 结论 |
|---|---|---|---|
| 加 Divide（1 文件） | 8.0s | 22.0s | 协作亏 |
| web（6 文件，机械改） | 18.1s | 24–32s | 协作亏 |
| many（16 文件，机械改） | 12.1s | 24.1s | 协作亏 |

这三个任务的共同点：**单 agent 一次就装得下**。机械改文件时它一步能写一个文件，串行成本极低，协作的讨论 + 审核开销占比超过 40%。

拿这种数据说「协作更快」是骗人。下面是换了任务形状之后的结果。

## 场景 A：3 个模块（auth / store / web）

每个模块都要「实现 + 写测试 + 跑通」，不是机械改。

| | 墙钟 | 主执行 | 审核 | token | 额度 |
|---|---|---|---|---|---|
| 单 agent（串行做完 3 个） | 43.9s | 43.8s | — | 113k | 12 |
| 单 agent + 审核 | 45.3s | 34.7s | 10.6s | 75k | 8 |
| **团队**（架构师 + 3 并行 + 审核） | **46.7s** | 讨论 4.3 + 并行 28.8 | 13.6s | 155k | 21 |

**打平。** 并行确实赢了（28.8s 做完本来要 78.8s 的活），但：
- 讨论 4.3s + 审核 13.6s = 17.9s 的协调成本；
- 每个 worker 都比单 agent 慢——它多背了「架构师方案 + 职责说明 + scope 限制」，单 agent 一个模块只要 11.5s，worker 要 22–29s。

净收益 ≈ 5.7s，协调成本 ≈ 7.3s，所以打平。

## 场景 B：6 个模块（auth / store / cache / queue / api / web）

规模翻倍，并行度从 3 提到 6。

| | 墙钟 | 主执行 | 审核 | token | 额度 |
|---|---|---|---|---|---|
| 单 agent | **90.6s** | 78.4s（26 步 / 33 工具 / 12 文件） | 12.1s | 280k | 29 |
| **团队 6 并行** | **42.6s** | 讨论 4.8 + 并行 27.3s | 10.6s | 282k | 36 |

**团队快 2.1 倍。** 并行把 154.2s 的串行活压到 27.3s（5.6× 加速），讨论和审核的固定开销被摊薄了。

单 agent 的 78.4s / 26 步是它自己的真实成本——六个模块、每个都要写测试并跑通，它必须一件件来。

## 结论

**决定团队协作有没有意义的是「任务能不能切成互不阻塞的块」，不是文件数量。**

| 任务形状 | 团队是否值得 |
|---|---|
| 1 个模块、需求明确 | 不值得（8s vs 22s） |
| 16 个文件的机械改动 | 不值得（12s vs 24s） |
| 3 个独立模块（各需实现+测试） | 持平（46.7s vs 45.3s） |
| **6 个独立模块** | **值得（42.6s vs 90.6s，2.1×）** |
| 模块之间有强耦合 | 不值得（拆不开就别拆） |

换算成宣传口径可以说：**互不依赖的模块 ≥4 个、每个都需要真实实现和验证时，1 个架构师 + N 个并行开发能把交付时间压到单 agent 的一半左右；成本基本相当（token 相同，额度因多跑几个 run 略高）。**

## 质量：各有短板，都要说

**团队版**
- 4 个模块绿、1 个红：`web` 的测试用正则解析 JS，**遇到嵌套 `then` 就误报**——代码其实是对的（`setState('error', msg)` 在 `readError().then()` 里），测试却断言失败。
- 这是并行 worker 的典型问题：想证明自己做得好，写出**过度解析实现细节**的测试。

**单 agent 版**
- 全绿，但审核指出：`cache` 的并发测试只断言 `Len() <= 8`，只要不崩就成立，**抓不到丢更新**；`store` 的 `TestConcurrentAccess` 32 个 goroutine 里**一个断言都没有**。

所以两边的「绿」都要打折看。这也说明**审核轮不是可选项**——两种模式下，只有跑一遍审核才知道测试到底有没有在测东西。

## 成本

token 基本一样（280k vs 282k），额度差 24%（29 vs 36）——多出来的 run 各自付了一次 input。

## 复现

```bash
# 团队（6 并行）
python3 scripts/team_bench.py --case six --root /tmp/dsh-team6

# 单 agent 对照
python3 scripts/team_bench.py --case six --root /tmp/dsh-team6-solo --solo
```

原始数据：`docs/team-six.json` / `docs/team-six-solo.json` / `docs/team-modules*.json`

## 前提（不满足就别看上面的数字）

1. 模块之间**没有共享代码**（有耦合时并行会互相踩，`scope` 会挡住，但工期不会缩短）
2. 每个 agent 的 `scope` 是独立目录
3. 并行上限已提到 6（`maxParallelRuns`），再高就得先解决「谁来看时间线」
